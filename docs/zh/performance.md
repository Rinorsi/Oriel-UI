# 粒子与动画性能：开工前必读

[制作流程](ui-workflow.md) · [脚本合同](scripting.md) · [验收](validation.md)

这份规范适用于页面作者和 agent。保护上限不等于流畅预算：脚本没超时、strict 没报错，都不能证明游戏里不卡。先保留数量、种子、轨迹、进退场和交互，再优化执行方式；不能靠删特效或缩短播放伪装性能提升。

## 开工前确定绘制路线

| 内容 | 使用方式 | 原因与限制 |
|---|---|---|
| 文字、按钮、布局、原生物品与角色 | 原生页面元素；缓存引用 | 保留字体、命中、布局和 Minecraft 渲染能力 |
| 少量独立装饰 | 复用节点，使用已有动画句柄 | 结束、取消、重播时回收；先测高峰 |
| 密集的纯装饰粒子 | 按前后层共享少量 Canvas，统一帧循环 | 不要一颗粒子一个 Canvas；Canvas 仍由 CPU 栅格化 |
| 旋转矩形、线段、四边形火花 | 新版 Canvas 的 fillQuad，一次提交四个顶点 | 原生扫描线；不是浏览器完整 Path2D，详见脚本合同 |
| 小图标粒子 | 复用离屏图集与 drawImage | 只支持 Canvas 来源，最近邻；旋转图集需说明角度量化差异 |

## 不能这样写

- 密集粒子逐个 createElement、插入/删除节点、修改 class 或启动独立 DOM 动画。树和选择器相关变动可能触发全树重新匹配，不能当成 GPU 精灵批次。
- 在每颗粒子的每帧里解析 transform 字符串、正则拆数值、查询选择器、getComputedStyle 或读布局再写布局。预先保存引用、几何和数值参数，帧内只做必要插值。
- 在 JavaScript 中逐像素或逐扫描线绘制旋转图形。用 fillQuad；图片用共享图集，不能给每颗粒子重建、解包或复制图集。
- 把所有内容塞进全屏 Canvas，或每颗粒子新建 Canvas。文字、实体、物品、复杂遮罩仍走各自支持的原生能力；Canvas 没有自动 GPU 加速承诺。
- 反复写 width/height 来清屏（会重新分配表面），或者活动粒子为零仍保留循环。清屏用 clearRect；关闭、重复触发、重播、离页要取消延迟任务、动画句柄和帧回调。
- 把静止期间的 60 FPS 当动画性能，把离线预览耗时当 Minecraft FPS，或只测一页就声称所有模板已优化。
- 直接放宽沙箱限额来掩盖卡顿，或为了性能删掉退出动画、粒子数量、光效层次。

## 怎么验收

1. **保留基线**：固定库版本、页面文件、随机种子、尺寸、GUI 缩放与动作序列。先录最卡阶段，再改代码；区分首次加载与持续播放。
2. **分清开销**：游戏用 JFR/性能采样确认脚本、样式/布局、CPU 绘制、纹理上传、GC 的占比。离线预览可定位 CPU 热点，不能证明游戏 GPU 和帧率。
3. **一次改一层**：图集采样、扫描线、节点或定时任务分别对照。新版 drawImage 复用行缓冲并预计算横向采样；小范围自拷贝仍保留快照，不改变重叠语义。
4. **重复最重动作**：至少三轮同一段动画，另测连续触发五次、结束、重播、关闭再打开、减少动效。记录中位耗时、长帧/低帧和分配量；基准期间不要并行构建。
5. **检查画面与清理**：640×360、427×240；数量/轨迹和关键阶段截图对照；连续触发后任务、节点与内存不能不断累积。未实测的环境明确标注。
6. **形成回归**：引擎修改先添加能复现问题的用例，再修改实现。像素对照覆盖 alpha、裁剪、缩放、重叠自拷贝、源更新/resize；性能预算测试避免依赖某台机器绝对 FPS。

60 FPS 的整帧预算约 16.7 ms，属于游戏和全部模组共同使用。每页应按目标机器制定自己的预算；不存在一个通用的“安全粒子数量”。已有画布像素上限见 [安全与设置](security.md)，不能用它代替性能测试。

## 库升级与交付

页面保存可以热重载，Java 引擎或脚本绑定改变需要更新 jar 或重启开发客户端，不能说保存页面就换了库。使用 fillQuad 前检测 `typeof ctx.fillQuad === "function"`；旧版可以保留已测的扫描线兼容实现，但必须说明旧版不享有这项优化。

发布前对准确的提交内容执行测试、严格 UI 检查、后端边界检查和目标加载器构建。日志、JFR、截图、运行目录、个人模板与原视频素材留在工作区，不加入库提交。只上传源码、必要回归与维护文档，核对 GitHub 仓库、账号和实际远端提交。
