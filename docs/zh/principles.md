# 产品定位与 agent 工作准则

做任何改动之前先读这一页。它回答两个问题：**Oriel 是什么、不是什么**，以及 **agent 怎么做才符合产品设计**。每条准则后面写了来由，不是凭空的规定。具体怎么做页面见 [做页面前先读](page-rules.md)，怎么热更新见 [热更新](hot-reload.md)，版本变化见 [更新与升级](upgrading.md)。

## 1. 它是什么，不是什么

- **是**：一个 Minecraft 的**界面库**。用 HTML/CSS/JS 写界面，Minecraft 当浏览器渲染；给模组作者用，也给想自己写 `.html` 放进游戏预览的玩家用。
- **不是应用**。物品编辑器、商店逻辑、任务系统这类**应用功能不放进库**，它们属于用库做出来的模组或页面。（0.11 把物品编辑器移出库，就是这条。）参考副本在工作区 `research/oriel-item-editor-reference/`。
- **不是浏览器**。不提供 SVG、iframe、WebGL、video、audio 标签；声音走 `oriel.playSound`。不能说"任意 H5 都能转成游戏界面"。
- **库的职责**：提供外壳、控件、动效、字体、图标、热更新、检查工具、可复用的示例。其余交给下游。

## 2. 十条准则（agent 必须照做）

1. **默认不改变原版。** 会改变原版界面或行为的功能必须**默认关闭**并可配置。例：库不往原版界面里注入任何东西（没有 Mixin，也不替换原版背包旁或 HUD 上的效果图标），这类界面只做预览，放进游戏由下游模组自己写；快捷键在玩家环境默认不绑定；`dev-sources.properties` 在任何环境生效，所以不发给玩家。*来由：用户装上库，原版背包被换了，却没有要求过。*
2. **点开必须有内容。** 列表里的每一项（演示、模板、命令）打开后都要有可看的东西；做不出来就别列出来。旧遗留页要么大方展示（带"旧版自带"标签）、要么删，不留莫名其妙的入口。*来由：showcase 里混着打开什么都没有的页面。*
3. **showcase 是主参考，模板和预设是次级。** 做某类效果先 `node tools/showcase/query.mjs <关键词>` 找现成实现再改，不从零发明。新增示例页必须同一次变更里登记索引。见 [Showcase 导览](showcase.md)。 写行、格子、弹窗、列表、提示这类通用部件之前，先在已有的页面、`ore.css` 和公共脚本里搜一遍有没有现成的；同名全局函数只留一份（检查器会提示 `duplicate-global-function`）。
4. **字体字号照表，不猜。** 中文用 `oriel:pixel_12` 的 12px，标题 24px；8px 汉字会糊。文字不能出框：长文本用省略号加悬停提示（tooltip）。见 [做页面前先读](page-rules.md)。
5. **边改边看是默认工作流。** 先配好热更新（[热更新](hot-reload.md) 里五种情形选一种），再动手做页面；把 640×360 和 427×240 的截图发给用户，不自己宣布"好看"。要正式放进模组或仓库时才走验收、批准、接入。
6. **不要自己发明开关。** 热更新、页面预览、文件夹页都有官方做法；"开发时改读文件夹页""复制文件加监视脚本"之类的绕路一律不要。
7. **公开 API 要真实存在并进快照。** 文档里写的类必须是公开的（`dev.oriel.mod.client` / `server`），并列入 `api/*.txt`；`dev.oriel.mod.internal` 下的东西不对外，也不能在手册里当 API 写。*来由：文档写了 `OrielPages.folder`，类却在 internal 里。*
8. **不兼容就升 minor，同时写升级说明。** 1.0 之前，不兼容的受支持变更提升 minor 版本（0.10 → 0.11），依赖范围随之变；改了 `CHANGELOG.md`，也要在 [更新与升级](upgrading.md) 里写迁移表。
9. **文档同步是完成条件。** 改能力、命令、默认值、API，同一次变更里更新手册；只维护中文这一套；新增文档要在 [首页](index.md) 登记。没做、没测的不要写成已支持。
10. **汇报要分清"实测"和"没验证"。** 说"好了"之前写明哪些在真实游戏里跑过、哪些只是编译或预览、哪些完全没测。别人没验证的结论不替他们背书。

**复刻任务**（把已有的动画、网页、原版界面复刻成页面）另有一套更严格的开发者流程：[复刻流程](replication.md)。普通做页面不适用。

## 3. 动手前自问（决策流程）

- 这个功能是**库的能力**，还是**某个应用**？应用 → 放下游，不进库。
- 它会**改变原版吗**？会 → 默认关闭，写进配置表（[安全与配置](security.md)）。
- 页面里有没有**点开是空的**入口？有 → 补内容或删掉。
- 有**现成的示例**吗？先查 showcase 索引。
- **公开 API** 变了吗？→ 快照、边界测试、手册、升级说明都要动。
- 我写的每一句"已支持"，**真的跑过**吗？

## 4. 团队协作（同一个仓库不止一个会话）

- 共享工作树里可能有别的会话的未提交改动。**只暂存自己改的文件**；同一个文件里有别人的改动时，只暂存自己的那几处，不要 `git add -A`。
- 构建、测试、游戏验证的日志写进工作区 `daily/<日期>/`，不进仓库。
- 提交前跑 `tools/repo-hygiene.sh`。

## 5. 不要做的事

- 往库里加应用功能；默认替换原版界面；列出点开没内容的页面。
- 手写一套颜色、字体、动效时长，不用 `ore.css` 的变量和 `m-*` / `fx-*` 类。
- 用 `../textures/…` 引用库资源（只在库自己的目录里有效），外部页面写 `oriel:textures/…`。
- 为了测试工具而启动游戏客户端（用户没要求时）。
